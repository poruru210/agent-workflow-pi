## Mandatory global execution workflow

Before substantive task action, first apply this bootstrap classification. A task may use the compact branch without reading the detailed policy only when all of these are affirmatively true: it is short, single-purpose, read-only, and low-risk; it needs no implementation, file or setting change, diagnostic/test execution, formal code review or audit beyond the detailed policy's low-risk simple-review exception, external-action planning, external write, delegation, multi-agent work, correction cycle, release/operation decision, or persistent checkpoint; its answer will not be used to authorize, plan, or materially influence an external action or other material decision; it does not depend on volatile identity/freshness; and a wrong answer cannot cause material medical, financial, security, safety, privacy, legal, production, or irreversible harm. Record only `objective/question, target/source, source time or version, allowed scope, answer and limits`. If any condition is false or uncertain, the work grows beyond that compact record, the user requests code review/audit outside that low-risk simple-review exception, implementation, external-action planning, delegation, or a material issue appears, enter the normal workflow and load the applicable sections of `~/.pi/agent/workflow/global-workflow.md` before the substantive phase or gate that needs them. The bootstrap requirements below are the always-on invariant set for the normal workflow. Do not sequentially read the entire detailed policy merely to enter the normal branch: first inspect its heading index, then read the sections governing the current work type, phase, evidence route, delegation/audit decision, and any cross-reference needed to resolve a material ambiguity. Expand to additional sections when a decision can materially depend on them; use a full-file read only as a fallback when applicability cannot be bounded. The detailed policy remains the sole detailed source of truth; section-scoped loading is a Pi runtime optimization and does not relax unread applicable rules. Higher-priority instructions and more specific applicable project instructions still control scope and permissions.

Bootstrap requirements:

- Optimize for efficient achievement of every frozen primary objective and mandatory acceptance criterion. Plans, baselines, tests, audits, and subagents are means, not output metrics. Stop when the required outcome, evidence, and acceptance boundary are satisfied; budget exhaustion alone is neither success nor completion No-Go.
- Do not obtain stability by uniformly suppressing model capability, exploration, reasoning depth, or creativity. Bound the work with the primary objective, authority, source of truth, acceptance criteria, evidence, phase gates, and stopping conditions; within those boundaries use the selected model's sufficient capability. Guarantee the minimum quality through outcome and independent-refutation keys, diagnosability, reachability and impact judgment, and proportionate verification, not by accepting a disabled or prematurely terminated primary function.
- The compact branch above ends when its answer and limits are delivered; it never grants change authority or supplies implementation, release, external-action, or audit PASS evidence. In the normal branch, freeze the risk-proportional work definition, objective ledger when needed, baseline applicability and evidence, time/efficiency budget, and exact active step. Preserve a durable checkpoint for long, delegated, multi-objective, external-action, or correction-heavy work so context compaction cannot replace the source of truth.
- Pass every new issue or improvement, including subagent findings, through the objective drift/value gate before changing the active step. Only mandatory same-scope work or a bounded efficiency enabler whose cost is recovered within the current task may interrupt; separate, reject, or briefly record everything else.
- Classify implementation packages as new implementation, existing-defect repair, or maintenance/migration. New work crosses design readiness including prospective verification-capability and causal-intervention impact design; repairs keep raw observations separate from the parent's provisional causal interpretation, assess detection responsibility, classify any applicable verification-escape packet as confirmed, affirmatively not applicable, or unproven, and cross the applicable blind-first read-only root-cause challenge before correction; maintenance crosses change, intervention-impact, and verification-applicability readiness. Before any candidate-bearing change, freeze its externally observable intended semantic delta, supported normal-success envelope, allowed stop domain, contracts that must remain unchanged, the causal or design link being changed, shared mechanisms and reachable consumers, and material new failures the intervention could induce. After the snapshot, independently reconcile those predictions with the derivable actual delta and bounded impact cone. For stop-capable changes, also close aggregate guard composition, dominance or dead guards, each guard's unique prevention, diagnosis, or recovery role, normal-path preservation, and recovery liveness; treat fail-closed as behavioral containment rather than mere diagnostics. Preserve model capability and the observable normal success path while designing proportionate diagnosability without excessive logging or hot-path cost.
- Keep phase order explicit: root-cause challenge occurs after diagnosis and before correction; pre-action audit occurs after action readiness and before an external write; early implementation/test-readiness audit occurs only after an implementation-complete frozen snapshot and before behavioral tests; final audit occurs only on the tested release candidate. Never change the audited target during audit or correct findings before the audit and disposition are complete.
- For work combining code changes with external writes, use the policy's composition gate: test/sandbox writes occur only after early audit and guarded test transition, while deploy/publish/production writes occur only after release-candidate and final-audit readiness. External authority, freshness, action audit, and result verification are never implied by code approval.
- Delegate only when critical-path, quality, independence, or risk benefit exceeds instruction, startup, waiting, integration, duplication, and reverification cost. Use a bounded job lease; reuse an agent only for the same job identity. Wait, correct, retire, or respawn through the explicit lifecycle gate, and replace a nonresponsive required audit only with equivalent independent coverage rather than duplicate wait-interrupt loops.
- Choose execution allocation and verification allocation separately. Task size, simplicity, or parent-direct execution does not lower assurance. Completion needs an outcome key and an independent-refutation key: independently check that the original request and source of truth were completely mapped into objectives and acceptance criteria. Meaning-bearing root-cause claims may not use the parent's causal interpretation as both keys: except for the detailed policy's strict deterministic closure, an independent blind-first derivation must start from the fixed raw evidence before reconciliation. For candidate-bearing changes, close the intended intervention, intended-versus-actual semantic delta, preservation contracts, bounded impact paths, and reachable material change-induced failures before completion. Freeze the initial verification universe from requirements, normal-success envelope, state model, preservation contracts, root-cause and intervention predictions, and planned impact before implementation; after the snapshot, blind review and actual-impact reconciliation may add coverage but may not silently delete, weaken, quarantine, or rewrite precommitted cases or oracles. Track every post-failure test intervention, leave uncovered impact branches unresolved, and reject PASS that depends on candidate-bearing state pollution or a requirement-unbound threshold change. Route every mandatory claim through deterministic closure, one bounded independent review, or separated non-overlapping reviews when correlated blind spots or material harm require them. Count coverage of unresolved failure modes, not agents; use blind-first, non-test-dependent review, reuse unchanged evidence, and review only affected deltas.
- Treat whole-artifact hashes as identity and change-detection evidence, not automatic invalidation of every prior audit claim. Maintain a claim-level evidence dependency map and, before any audit-test or audit-correction re-entry, identify the unresolved objective or acceptance claim, the identity-bound change or genuinely new evidence, the exact dependent claims invalidated, the decision the next pass can change, and the unchanged evidence to reuse. Re-audit implementation deltas, test-plan deltas, new evidence, and volatile external-state deltas through their matching bounded route; expand only when the dependency boundary is unproven or a reachable material path crosses it. Do not repeat a terminal review key because wording, reviewer, model, hash alone, or the same evidence changed presentation. Lack of new decision-bearing information stops the duplicate loop and triggers diagnosis, replanning, residual-risk disposition, or the appropriate bounded No-Go, but never converts an unmet primary objective or mandatory unproven claim into completion.
- Before every subagent turn, show the user the job, the model name exposed by the current model catalog or delegation runtime, requested reasoning, and selection rationale. Select model and reasoning separately from current capabilities, fix capability sufficiency before optimizing total cost, and avoid fixed names or old rankings. When the delegation runtime accepts explicit model/reasoning and creates the job without reporting rejection, downgrade, mismatch, or ignored overrides, record the request as `delegation runtime accepted`; do not ask the child to self-report metadata it cannot inspect or repeatedly report that limitation. Use returned effective metadata when available, and reject only evidenced mismatch or genuinely unproven configuration for mandatory evidence.
- Do not patch from the first error or stop every independent safe partition. Preserve a source-identified raw evidence dossier without causal labels, separately build the parent's provisional causal ledger, establish the last-good-to-first-fault chain and affected scope, and challenge material alternatives through the detailed policy's blind-first dual-key root-cause gate. Resolve parent-reviewer disagreement with the smallest safe discriminating evidence; do not settle it by authority, majority, or patch plausibility. Separately assess detection responsibility and trace any applicable verification escape from requirement and risk through selection, setup, the real path, behavioral oracle, and reporting or enforcement toward its earliest break. Before correction, bind the causal link being changed to shared mechanisms, reachable siblings and consumers, preservation contracts, counterfactual predictions, and material new failure hypotheses; map them to precommitted behavioral and preservation oracles. Classify the escape packet as confirmed, affirmatively not applicable, or unproven; do not turn unproven into automatic No-Go outside the detailed policy's mandatory-acceptance or high-harm conditions. Batch product and verification corrections by root cause, freeze a new snapshot, perform only the affected early re-audit, and then run observable partitioned tests. Test-plan-only changes use a versioned supplement and delta screen rather than a new implementation snapshot.
- Treat the product root cause, an escaped product failure, and a faulty verification model as separate claims. When state, identity, event families, ordering, clocks, observation, fixtures, oracles, or fail-fast masking affect a result, maintain the detailed policy's verification-model and test-system-root-cause records rather than patching the next assertion. Continue a test correction only when it is mandatory or decision-bearing, has new discriminating evidence and a falsifiable prediction, addresses the shared cause, and has greater risk-adjusted value than the next eligible primary-objective work. Otherwise retire, defer, partially bypass, block only the dependent release claim, or request a decision as specified by the policy; never convert an invalid, skipped, quarantined, or abandoned test into PASS. Do not use a fixed correction count as the stop or continue rule, reset a cause by renaming or versioning the test plan, or re-enter without new decision-bearing evidence.
- Apply reachability, change causation, material harm, diagnosability, containment, and recovery before correcting audit findings. Hypothetical, unsupported, invariant-blocked, or unreachable paths require affirmative evidence and do not justify disabling the primary function. `Unproven` is an evidence state, not automatic No-Go.
- Completion requires every mandatory objective's observable normal-path outcome, every mandatory acceptance criterion, applicable diagnosability, candidate identity, required evidence layers, and required audit disposition to PASS or have an explicit user-approved exception. Report continued work, replanning, user-decision wait, technical blocker, operation No-Go, release No-Go, and completion No-Go as distinct states.

Do not claim that this workflow is empirically superior from document self-review alone. Use the policy's objective evaluation boundary: distinguish structural design PASS from demonstrated improvement in outcome achievement, missed defects, convergence, rework, elapsed time, token/tool/delegation cost, and scope drift across representative tasks.

## Pi runtime binding

This section binds the product-neutral workflow to the current Pi runtime; it does not add or replace workflow policy.

- Policy loading on Pi is section-scoped. `global-workflow.md` is workflow policy, not Pi product documentation, so Pi's guidance to read Pi documentation files completely does not require a whole-file policy read. At normal-branch entry, inspect the heading index once (for example with `rg -n '^#{1,4} ' ~/.pi/agent/workflow/global-workflow.md`), load the sections applicable to the current work type and immediate phase/gates, and remember which unchanged sections are already loaded for the session. Do not issue overlapping whole-file reads. Load a cross-referenced or previously unread section when it can change the current decision; full-file loading is the fallback for genuinely unbounded applicability.
- Use the installed `pi-subagents` `subagent` tool directly for delegated jobs and independent reviews. In the detailed workflow, runtime-specific references such as `orchestrator`, `orchestrator accepted`, spawn/follow-up, or effective model metadata map to the corresponding `pi-subagents` launch/runtime evidence on Pi. Do not recreate subagent execution, chaining, parallelism, lifecycle, usage accounting, or cancellation in this repository unless a measured gap requires it.
- Delegation is an execution mechanism, not a separate user-granted capability. Do not require the user to explicitly ask for a subagent. If the user's request already authorizes the underlying read/write/test/review operation and no higher-priority instruction or user instruction forbids delegation, a bounded child may perform only those same authorized operations; it never gains broader authority than the parent. User silence about subagents is not a prohibition.
- Custom workflow roles live in `~/.pi/agent/agents/*.md` and are discovered by `pi-subagents`. Each delegated turn still requires the bounded Job Lease defined by the detailed workflow. Before the first launch in a decision point, use `subagent` list/discovery as required by the installed runtime, then launch only an executable role.
- Optional implementation/research worker allocation and mandatory independent verification are separate decisions. A decision to implement directly in the parent does not waive T1/T2 or any other required independent-refutation coverage. When the detailed workflow requires independent review and `pi-subagents` can provide an eligible independent child, obtain that review before claiming completion unless an equivalent independent route closes the same claims. Parent self-review, tests, task smallness, or the absence of an explicit subagent request cannot substitute for required independent coverage.
- Use `workflow_models` to inspect the live Pi model catalog (availability, context, modality, reasoning support, and price metadata) whenever those facts can materially affect delegation value or model selection. Catalog inspection is not delegation and may occur before the optional-worker delegation gate; this avoids deciding that delegation is uneconomic without first knowing the currently available capability/cost envelope. After capability sufficiency and the required reasoning level are fixed, compare the current numeric `costPerMillionTokens` fields for the sufficient candidates whose billing units are directly comparable. Do not infer relative cost from model-family names, `mini`/`flash` labels, provider prestige, package examples, or an informal "upper/lower model" hierarchy. A same-billing-regime candidate that is no more expensive on every relevant input/output/cache rate and strictly cheaper on at least one is cost-dominant; do not select a dominated candidate on a cost rationale. If rates trade off, estimate the job's expected input/output/cache shape and choose the lower expected total cost; if billing units or quota multipliers are not comparable from the catalog, say that cost is not directly comparable rather than inventing an ordering. Final model and reasoning selection still follows capability sufficiency and the detailed workflow's evidence requirements.
- For independent-review jobs, use fresh child context unless the detailed workflow explicitly permits same-job continuation. Child execution success is runtime evidence only; it is never semantic PASS by itself.
- For a read-only review or audit whose result is consumed immediately by the parent and no later workflow step requires a durable named child-output file, set that `runs.run(...)` child to `output:false` and consume the returned inline result. Keep pi-subagents lifecycle/debug artifacts enabled; do not make the child write an additional authoritative output file merely for evidence retention. Use an explicit durable output only when a later step genuinely needs a stable file reference, and do not apply this rule to implementation/writer jobs that require such an artifact. This avoids unnecessary child-side artifact writes and platform-invalid generated output paths without weakening review evidence.
- Apply the detailed workflow's risk classification to the actual task target and effects, not to domain vocabulary or hypothetical production use. A local or sandbox fixture that models billing, finance, security, or another sensitive domain is not high risk merely because of that subject matter; classify from the actual write target, reversibility, external effects, sensitive-data exposure, and plausible harm if this task is wrong.
- When identity evidence crosses a Git object and a Windows working-tree file, distinguish Git-blob identity from filesystem-byte identity. Compare hashes only within the same byte representation, or explicitly normalize line endings before comparison; do not treat an LF-versus-CRLF-only hash mismatch as a candidate change or evidence conflict when the semantic content and intended identity boundary are otherwise unchanged. Record which representation each identity claim uses.
- When one required child result gates the next step and the parent has no useful independent work to do meanwhile, prefer a foreground single-child run (`async:false`) and consume its direct result. Use background execution when detachment or real concurrency has critical-path value; do not add wait/status/artifact inspection merely to recover a result that a foreground run can return directly.
- Follow the installed pi-subagents skill's matching-reference requirement. For an ordinary single-child decision and launch, read only the exact reference files required by that skill for the current path, avoid unrelated reference files, and do not reread unchanged references within the same parent session. Treat package-mandated reference loading as runtime guidance rather than workflow evidence.
- Early/final audit labels alone do not require different model families/providers or high reasoning. For materially similar bounded T1 review jobs in the same parent task, keep a capability-sufficient model/reasoning pair as the incumbent when it remains available and cost-competitive; do not churn to a more expensive model without a concrete capability, risk, availability, or expected-total-cost reason. Fresh child context supplies review independence; model-family novelty by itself does not. Select the lowest expected-cost currently available model and reasoning level that satisfy the concrete Job Lease, using the numeric catalog comparison above, and diversify model/provider only when the detailed workflow requires T2 or there is concrete evidence of a material correlated blind spot that the additional independence can reduce.
- The detailed workflow decides whether delegation, T0/T1/T2, early audit, final audit, or another evidence route is required. The runtime binding only supplies the mechanism.
